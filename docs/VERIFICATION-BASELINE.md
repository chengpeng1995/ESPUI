## 实机滑动性能

同一台设备，以 USB `@UI bench scroll` / `bench list` 在 UI 线程执行连续往返滑动。每次采样约 4.8 秒；桌面测试为前两个入口往返，设置测试为 250 px 上下滚动。记录 LVGL `RENDER_READY` 以及传输任务实际完成的整帧数；这不是面板自身扫描频率，也不是全应用最高/最低帧率保证。

| 场景 | 修改前 FPS | 优化后 FPS | 优化后帧间隔 P95 |
| --- | ---: | ---: | ---: |
| 桌面滑动，Wi-Fi/BLE 关闭 | 15.83 | 46.94 | 25.22 ms |
| 设置列表，Wi-Fi/BLE 关闭 | 15.42 | 44.50 | 23.54 ms |
| 桌面滑动，Wi-Fi/BLE 开启且已有扫描结果 | — | 45.90 | 25.67 ms |
| 设置列表，Wi-Fi/BLE 开启且已有扫描结果 | — | 43.28 | 24.16 ms |

上述为**中间版本**：虽然提高了绘制帧率，用户确认滑动时图像仍横向错开，属于画面撕裂，不能算显示问题解决。证据：`logs/device-bench-baseline.log`、`logs/device-bench-optimized.log`、`logs/device-bench-radios.log`。

随后增加整帧双缓冲和 GPIO13 TE 同步，80 MHz QSPI 独立传输；按实测约 16.91 ms 的面板扫描周期调整发送相位，避免写入追上当前扫描或被下一次扫描追上。CPU1 绘制、CPU0 发送，亮度命令与发送互斥。最终测量（Wi-Fi/BLE 均开启）：

| 最终同步版本 | 实际完成帧率 | 渲染帧间隔 P95 | 同步超时 / DMA 错误 |
| --- | ---: | ---: | --- |
| 桌面往返滑动 | 29.35 FPS | 35.54 ms | 0 / 0 |
| 设置列表滚动 | 29.42 FPS | 35.00 ms | 0 / 0 |

证据：`logs/device-te-final-bench.log` 中 `PRESENT` 为完成整帧发送计数，`BENCH` 为提交渲染计数，两者采样边界可能相差一帧。设备返回桌面时已发送 294 帧，TE 边沿 1,412 次，堆完整性检查为 1，内部可用 42,211 B、PSRAM 可用 3,959,316 B。最终接近 30 FPS，未达到严格的持续 ≥30 FPS 门槛。普通周期 `refresh_fps` 包含静止时间，不能用于动画帧率比较。

2026-10-09 用户在最终固件上左右滑动，现场确认原先横向错开、分段的现象“已经消失，画面完整”。这是实屏撕裂修复的人工验收，区别于上面的自动帧率计数。

其他性能修复：真机移除重复圆形根裁剪及整页透明合成，大按钮改为位移/颜色反馈，分页点仅在选中页变化时更新，LVGL 刷新周期 16 ms；两个 20 行内部 DMA 缓冲避免临时 PSRAM→DMA 拷贝分配失败。亮度设置和首屏创建放在绘制任务启动之前，修正启动时屏幕命令并发。

## 固件备份与恢复

烧录新系统前已完整读取设备 16 MiB Flash（含当时配置），文件位于上级目录：

`../backups/device-before-assistant-2026-10-09.bin`

SHA-256：`4d28640833b5bd741edd3caa6171a8e096f390ea96a83e8b82d93b124379c62f`。

备份日志：`logs/device-backup.log`。常规烧录不擦除 NVS。备份可能包含设备原有配置，应保留在本机；本工程未上传它。

恢复会覆盖当前系统及配置，只有需要回退时才执行。先停止额度桥接，再用工程 Python 环境运行 esptool：

```bash
python -m esptool --chip esp32s3 --port /dev/cu.usbmodem101 --baud 460800 \
  write_flash 0 ../backups/device-before-assistant-2026-10-09.bin
```
